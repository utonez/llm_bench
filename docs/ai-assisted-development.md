# AI 輔助開發：使用方式與心得

> 本專案使用 **Claude Code**（Anthropic 的 AI 程式開發工具）協作完成。我是這個專案的發想人，負責提出想法、決定方向；AI 負責把想法實作出來。

## 我的角色：發想、決定方向、審核

- **發想**：我想做一個和金融業相關、而且需要在雲端長期運作的題目，比較幾個方向後，決定做「金融場景 LLM 選型評測」
- **決定方向**：每個階段要做什麼、做到什麼程度，都由我決定，例如題庫要有出處、受測模型要多比較幾個、儀表板要分頁並看起來更專業
- **審核**：AI 目前還沒有到不需要人工審核的程度。Claude Code 寫完程式碼後，我會再檢查一次內容，確認邏輯、資料來源和設定都合理，才決定合併與部署

| 我提出的想法與方向 | AI 的執行 |
|---|---|
| 題目要和金融業相關，並能展現雲端架構 | 列出可行的題目，比較優缺點與風險 |
| Azure for Students 申請不了，改用 GCP | 對照免費額度與服務，設計架構 |
| **題庫必須有出處，不能編造** | 找出公開資料集與政府新聞稿、確認授權、逐字比對原文 |
| 受測模型從 3 個增加到 5 個 | 實測候選模型是否可用，再加入評測 |
| 儀表板要分頁、首頁要有視覺化設計 | 改版前端，並在瀏覽器實際確認 |
| 每個 PR 是否合併、每次部署是否執行 | 撰寫程式、測試、Terraform、CI/CD 與文件 |

## 工作流程

1. **我提出想法與需求**：說明要做什麼、為什麼要做
2. **AI 規劃並實作**：先列出步驟與完成條件（見 [PLAN.md](PLAN.md)），再以 TDD 方式先寫測試、後寫程式
3. **我檢查內容**：看程式碼與 PR 說明、確認測試結果，並實際操作線上的儀表板
4. **有疑問就追問**：看不懂或覺得不合理的地方，請 AI 解釋依據或修改
5. **確認後才合併**：合併到 `main` 之後，由 CI/CD 自動測試與部署

## 為什麼一定要人工審核

開發過程中，AI 確實犯過錯。以下是實際發生的問題：

| 問題 | 怎麼發現 | 處理 |
|---|---|---|
| AI 一開始自己**編了題目** | 我追問「這些題目是從哪裡來的」 | 全部換成有出處的題目，並讓程式強制每題都要附 `source` |
| 第一次在雲端執行，Gemini 成功率只有 63% | 檢查錯誤類型，發現全部是 `rate_limit` | 原因是我們送出請求太快，不是模型的問題；加上呼叫間隔後回到 100% |
| gpt-oss 回傳空白答案 | 實測時發現 | 推理型模型的推理過程用光了輸出額度；調整設定並記錄原因 |
| gpt-oss-20b 正確率偏低 | 新增 120b 做比較時發現 | 部分答案被輸出上限截斷；放寬後正確率從 81% 提升到 90% |
| 部署後瀏覽器仍在執行舊的 JavaScript | 在瀏覽器檢查時發現 | 修正快取設定，讓自家檔案每次都向伺服器確認版本 |
| **一個測試失敗的版本被部署上線** | 部署後才看到測試結果 | 指令沒有在測試失敗時中止。之後加上 CI 與 `main` 分支保護：**測試沒過就無法合併** |
| 預設服務帳號擁有專案編輯權限 | 部署前的安全審查 | 用 Terraform 移除；相依套件也改為以雜湊鎖定 |

這些問題讓我更確定：AI 可以大幅加快開發速度，但結果是否正確、是否可信，仍然需要人來把關。

## 心得

1. **想法和方向要由人提出。** AI 很擅長執行，但做什麼題目、要求到什麼程度，決定了專案的品質。題庫有沒有出處、模型比較得夠不夠、頁面是否專業，都是我提出要求之後才改善的
2. **要追問「依據是什麼」。** AI 的第一版答案不一定有根據。追問出處之後，整個專案的可信度完全不同
3. **人工審核之外，也要有自動化的把關。** 「測試沒過就不能部署」最後是靠 CI 和分支保護來保證，而不是靠人或 AI 記得
4. **我要能解釋每一個設計決策。** 每個決策都記錄在 [ADR](adr/) 中，包含考慮過的替代方案，確保我理解並認同 AI 所做的每一個選擇
