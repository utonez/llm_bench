# AI 輔助開發：使用方式與心得

> 本專案使用 **Claude Code**（Anthropic 的 AI 程式開發工具）協作完成。以下說明分工方式、實際流程，以及過程中學到的事。

## 分工：我負責判斷，AI 負責執行與查證

| 由我決定 | 由 AI 執行 |
|---|---|
| 題目方向：從幾個候選中選擇「LLM 選型評測」，並判斷它和金融業的關聯 | 列出可行方案、比較優缺點與風險 |
| 雲端平台：Azure for Students 申請不了，改用 GCP | 對照各平台的免費額度、服務對應 |
| **要求題庫必須有出處**，不接受編造的題目 | 找出可用的公開資料集與政府新聞稿、確認授權、逐字比對 |
| 增加受測模型、儀表板分頁與視覺改版 | 實測候選模型、實作與在瀏覽器驗證 |
| 每個 PR 是否合併、每次部署是否執行 | 撰寫程式、測試、Terraform、CI/CD、文件 |

## 工作流程

1. **先規劃**：每個里程碑開始前先列出步驟、風險與完成條件（見 [PLAN.md](PLAN.md)）
2. **先寫測試再實作（TDD）**：先寫測試並確認它會失敗，再寫程式讓測試通過。最終有 122 個 Python 測試、15 個前端測試
3. **查官方文件，不靠記憶**：模型名稱、API 端點、免費額度都先查證或實際呼叫
4. **每個里程碑一個分支和 PR**：PR 說明寫清楚做了什麼、為什麼、怎麼驗證
5. **安全審查**：部署前用 AI 依安全檢查清單審查程式碼與實際的雲端設定

## AI 帶來的價值

- **速度**：一個人在幾天內完成後端、雲端架構、IaC、CI/CD 與前端
- **查證能力**：在實作前就發現 **GitHub Models 已於 2026-07-30 退役**、臺灣銀行匯率 CSV 會擋程式存取（改用央行的官方 API）
- **完整的驗證**：每次部署都在瀏覽器與雲端實際確認，不只看「指令成功」

## 實際發生的問題，以及怎麼被發現的

這些是最有學習價值的部分：**AI 會犯錯，所以流程要能抓到錯誤。**

| 問題 | 怎麼發現 | 處理 |
|---|---|---|
| AI 一開始自己**編了題目** | 我追問「哪裡抓來的」 | 全部換成有出處的題目；程式強制要求每題都有 `source` |
| 第一次在雲端執行，Gemini 成功率只有 63% | 檢查錯誤類型，發現全是 `rate_limit` | 是**我們的客戶端送太快**，不是模型的問題；加上呼叫間隔後回到 100% |
| gpt-oss 回傳空白答案 | 實測時發現 | 推理型模型的隱藏推理用光了輸出額度；調整設定並記錄日期 |
| gpt-oss-20b 正確率偏低 | 新增 120b 時比較發現 | 部分答案被輸出上限截斷；放寬後正確率從 81% 升到 90% |
| 部署後瀏覽器還在跑舊的 JavaScript | 瀏覽器驗證時發現 | 快取設定有誤，修正後自家檔案每次都向伺服器確認 |
| **一個失敗的測試被部署上線** | 部署後才看到測試結果 | 原因是指令沒有在測試失敗時中止。之後加上 CI 與 `main` 分支保護：**測試沒過就無法合併** |
| 安全審查發現預設服務帳號有專案編輯權限 | AI 依清單檢查實際的 IAM 設定 | 用 Terraform 移除；相依套件也改用雜湊鎖定 |

## 心得

1. **AI 是很強的執行者，但判斷要自己做。** 題庫是否可信、要不要多比較幾個模型、頁面是否專業，這些都是我追問或要求之後才改善的
2. **要追問「依據是什麼」。** AI 的第一版答案不一定有根據；追問出處，讓整個專案的可信度完全不同
3. **把檢查交給流程，而不是交給記憶。** 「測試沒過不能部署」這件事，最後是靠 CI 和分支保護保證，而不是靠人或 AI 記得
4. **我能解釋每一個設計決策。** 每個決策都記錄在 [ADR](adr/) 中，包含考慮過的替代方案
